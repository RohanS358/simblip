1. What we are making

1.1 One sentence

You draw it (or photograph it), SIMBLIP understands what the parts are and how they connect, shows its understanding for you to correct, and then it runs — with one undo step to take it all back.

1.2 Three ways in

InputExampleWhat the system has to know
ALive ink — strokes from pen, finger or mouse on the canvasA student sketches a battery, a resistor and an LED and joins them with linesWhich strokes form a symbol; what the symbol is; its orientation; which wire ends touch which pins; any value written beside it (“1k”, “9V”)
BPhoto or screenshot of a diagramPhone photo of a circuit from a textbook or the whiteboard; a screenshot from a PDFThe same, but from pixels: clean up the picture, find symbols, trace wires, read printed or handwritten labels
CSituation sketches — informal drawings of a physical set-upA ramp, a block on it, an arrow marked “5 N”, “m = 2 kg”, “μ = 0.2”Objects (ramp, block, spring, pulley), their spatial relations (on, attached to, left of), and the numbers that give them physical meaning

Output for all three: one structured description, the Scene IR (Section 3.2), compiled by deterministic code into SimScript — the language the app already runs, lints and renders. The model never writes canvas objects itself.

1.3 Domains, in order of delivery

WaveDomainWhy this order
1Analog & digital circuitsClearest vocabulary (~60 symbols), strict topology (a netlist), the app already auto-draws a clean schematic from a netlist, and the most common thing a student sketches.
2Mechanics (ramps, masses, springs, ropes, pulleys, pendulums)Needs spatial reasoning (“touching”, “on top of”) rather than wiring; the engine already attaches constraints by overlap, so relations are mostly geometry.
3Optics & waves (sources, lenses, mirrors, slits, screens)Fewer symbols; left-to-right layout already assumed by the engine.
4Graphs, trees, state machines, block diagrams (diagram() / DSA Lab)Different compile target, same recogniser plumbing.

1.4 Why not “just use a vision-language model”?

The design stanceThe recogniser proposes, the compiler decides, the user corrects. This is the same stance lib/sketch/recognize.ts already takes: “a wrong guess costs the user nothing — meaning still comes from behaviors the user attaches.”

1.5 Success looks like

2.2 What is missing (the real gaps)

  1. No learned recogniser. Everything today is template or rule matching. It degrades as the number of classes and writers grows — the $P approach compares to every template and has no notion of “I don’t know”.
  2. No topology extraction from messy drawings: wires that overshoot, nearly touch, cross without joining, or have junction dots. Today relies on “node snapping” at placement.
  3. No handwriting or label recognition — a value written beside a part (“10 kΩ”) is ignored.
  4. No photo input. Images become OCR text (attachments.ts says so plainly: “a circuit diagram yields little or nothing”).
  5. No semantics for mechanics sketches (ramp = static line at an angle, block on it = rigid body, arrow = force), and no way to say “I’m not sure”.
  6. No feedback loop. A user’s correction is not captured as a training example.
  7. No evaluation set, so accuracy can’t be stated, only felt.

3.1 The pipeline

3.2 The contract: Scene IR

The IR is the most important design object in this document. It makes the pipeline testable stage by stage, lets a human or Claude write ground truth by hand, and keeps the models replaceable: a better classifier tomorrow changes nothing downstream.

// lib/sketch/ir.ts  (full zod schema in Appendix A)
type SketchIR = {
  domain: 'circuit' | 'digital' | 'mechanics' | 'optics' | 'diagram'
  nodes: Array<{
    id: string
    cls: string                        // a COMPONENTS id, e.g. 'resistor', 'battery', 'block'
    conf: number                       // 0..1, calibrated
    alt?: Array<{ cls: string; conf: number }>   // top-3 for the correction menu
    bbox: [x: number, y: number, w: number, h: number]
    rot: 0 | 90 | 180 | 270            // pose; polarity lives here
    flip?: boolean
    values?: Record<string, string>   // { R: '10k' } — raw text; the compiler parses units
    source: 'ink' | 'photo'
  }>
  edges: Array<{ a: { node: string; pin: string }; b: { node: string; pin: string }; kind: 'wire' | 'rope' | 'rod' | 'spring' | 'damper'; conf: number }>
  labels: Array<{ text: string; bbox: number[]; attachedTo?: string }>
  doubts: Array<{ ref: string; why: 'low-confidence' | 'ambiguous-junction' | 'dangling-wire' | 'unreadable-value' }>
}

Rules: (1) Stages may only add or refine IR fields, never invent canvas objects. (2) Every low-confidence decision must also appear in doubts, because the UI shows them. (3) The IR is serialisable and small (a few KB) — it can travel to the tutor as part of the sketch.recognize tool result.

3.3 The compiler (no model)

DomainStrategyWhy
Circuit / digitalEmit create() and connect() with no x/y; the auto-layout engine draws the schematic.The user’s sketch only needs to be topologically right. Hand-drawn geometry doesn’t have to be preserved (and shouldn’t be — it is untidy). Optional “keep my layout” mode places by IR bbox.
MechanicsEmit create() with x/y from IR bboxes, attach rigidBody / staticBody by class, set parameters from labels; let the physics runtime resolve constraints by touching.Position is the information. “Ground below falling bodies” is already a rule in the generator prompt.
OpticsLeft-to-right on one axis; y from the sketch; f etc. from labels.Matches existing engine convention.

The compiler’s output goes through lintSimScript and autofixSimScript. If lint fails, the compiler has a bug, not the model — and the tests (Section 7) catch it on hand-written IR before any model exists.

3.4 Interaction design: “ghost, confirm, place”

  1. Ghost overlay. After pen-hold (live ink) or import (photo), draw the recognised parts translucent over the user’s own ink, each labelled (“resistor 10 kΩ”) with a coloured dot for confidence: green ≥ 0.9, amber 0.6–0.9, red < 0.6.
  2. Fix by tapping. Tap a part → the top-3 alternatives plus “draw it again” plus a full list. Tap a wire end → “connect / don’t connect”. Tap a value → type it.
  3. Place. “Make it live” replaces ink with real parts as one undo step (the same pushHistory guarantee used by AI edits). The original ink is kept on a hidden layer so Undo restores it exactly.
  4. Explain what you see. The tutor (Doc 1) can narrate the IR: “I read this as a 9 V battery in series with a 1 kΩ resistor and an LED. The LED symbol points the wrong way for current to flow — want to try flipping it?” That is a teaching moment the pipeline gets for free because the IR names things.
  5. Learn from the fix. A correction is stored locally as {strokes, correctedClass}; with consent it is uploaded to the same global table /train already writes to.

4.2 S0 — geometry and rules (extend what exists)

  • Stroke grouping. Strokes belong to one symbol if they are close in time (pen-up gap < ~600 ms, tuned on data) and their bounding boxes overlap or nearly touch. A capacitor is two parallel strokes; a battery several; a gate is a body plus a bubble. Grouping errors are a main failure source, so the grouping parameters are learned from the collected data, not guessed.
  • Wires. Long, near-straight, near-axis-aligned strokes, or polylines with right angles, that are not inside a symbol group. Their endpoints are matched to nearby pins (S1 gives a pin template per class; terminalsOf() gives real pin positions after placement). Overshoot and gaps below a tolerance snap. T-junctions with a dot connect; crossings without a dot don’t (the circuit-redesign phase already added hop arcs for unconnected crossings — the same semantics).
  • Arrows (forces, velocities, current direction): a line plus a short “V” head at one end; direction and length become an IR edge attribute for mechanics.
  • Ramp, ground, wall: long strokes classified by angle and by what is attached below/above; hatching (many short parallel strokes) means “fixed ground”.

4.3 S1 — SketchNet

Input design (this is where accuracy is won)

  • Normalise with the existing normalizeStrokes; strip leads with the existing stripLeads so the discriminating body fills the frame. Feed both the full and the body-only view (two channels).
  • Raster view: render strokes to 32×32 (anti-aliased, fixed 2 px line width). A tiny CNN handles shape.
  • Sequence view: resample each stroke to a fixed number of points (e.g. 64 total across strokes) as (x, y, penUp, direction-change). A small GRU captures how it was drawn (a zigzag resistor has ≥ 4 direction reversals; a battery has stroke-length asymmetry).
  • Fuse both embeddings → two heads: class (~100 classes + unknown) and pose (0/90/180/270 + flip). Polarity (diode direction, battery +/–) is a pose, not a class — avoids doubling the class count.

Why this should be small

32×32 inputs with ~100 classes is MNIST-scale. A 4-block CNN (channels 16-32-64-96) plus a 64-unit GRU is on the order of 150–400 k parameters est. — about 0.3–1.5 MB after int8 quantisation. If it turns out too weak, widen it; there is a hundred-fold margin before it competes with anything else in the memory budget.

Calibration and “I don’t know”

  • Train with an explicit unknown class (random doodles, letters, partial symbols) and apply temperature scaling on a validation set so confidence means something — the UI relies on it for the green/amber/red dots and for the top-3 menu.
  • Keep the existing $P/CART matcher as a fallback and ensemble member: if SketchNet’s confidence is low and the user has custom templates for this class, use theirs. Users who teach the app their own symbols (the point of /train) must never get worse.

Classes

See Appendix B. The list is generated from COMPONENTS plus mechanics/optics primitives; a class without a component to map to is a gap to report, not a class to invent.

4.4 S3 — text and values

  • S3a (ink). Segment characters (stroke grouping again), classify with the same architecture over ~80 symbols: digits, . , + − × / ^ = Ω μ π θ k M m n p V A F H Hz s N g °, a few Latin letters. Then a unit grammar turns “1 0 k Ω” into {R:'10k'}. Restricting the alphabet is what makes this tiny and accurate; free-form handwriting recognition is a much larger problem and is not attempted.
  • Association. A label belongs to the nearest part (distance in the part’s local frame, preferring “above/below the body”); ambiguous cases go to doubts as unreadable-value and the UI offers a keypad.
  • S3b (photo). Tesseract on label crops (not the whole image) with a digits/units whitelist — far more reliable than whole-image OCR, and cheap because crops are small.

4.5 S2 — detector for photos (only if needed)

Strategy: start without a detector. A clean textbook diagram can be binarised, split into connected components, and each component classified by S1 (rendered from the component’s pixels). That reuses S1 at zero extra megabytes. Add a nano detector only if the Phase S5 evaluation shows recall problems on messy photos (touching symbols, text overlap, shadows).

Licence trapThe popular Ultralytics YOLOv8/YOLO11 family is released under AGPL-3.0 (with a paid enterprise licence). Shipping it inside SIMBLIP would pull in obligations Rohan almost certainly doesn’t want. Prefer an Apache-2.0 detector (YOLOX-Nano, NanoDet-Plus) and re-check the licence of any pretrained weights before use.

4.6 S4 — tiny vision-language model (optional, last)

SmolVLM-256M and 500M are Apache-2.0 vision-language models published with ONNX and WebGPU demos; a Hugging Face write-up reports the 256M model runs single-image inference in under 1 GB of GPU memory and the 500M model needs about 1.23 GB; the paper reports up to 80 decode tokens/s for the 256M model in a browser on an M4 Max MacBook. These are vendor/press numbers, not CPU measurements on a 4 GB laptop.

Allowed jobs: (a) decide what kind of figure this is (circuit? free-body diagram? graph? text-only?) so the right pipeline runs; (b) caption it for the tutor (“a ramp with a block and a pulley”); (c) propose IR for informal situation pictures, flagged low-confidence. Forbidden: being the only source of wiring.

Memory rule: S4 and the tutor’s language model are never resident together. Photo import asks the engine lease to unload the brain, runs S4, releases it, and the brain reloads on the next chat turn (weights stay cached in OPFS). Decide whether S4 ships at all from the Phase S6 evaluation.

5. Data: where the training set comes from

A classifier is only as good as its data, and drawings are where public data is thinnest. The plan uses four sources and — crucially — never evaluates on synthetic data alone.

5.1 Source 1 — Synthetic strokes from SIMBLIP’s own part drawings

Every circuit part has a vector drawing in part-art.tsx; mechanics and optics primitives have shapes in the object renderers. Turn those paths into pen strokes and corrupt them the way real hands do:

// scripts/ai/sketch/synth.ts  (sketch of the generator)
for each class c, for each style variant v (IEC box resistor, ANSI zigzag, US/IEEE gates, …):
  paths = svgPathsOf(c, v)                       // from part-art / object renderers
  repeat N times:
    strokes = splitIntoPenStrokes(paths, strokeCount ~ real distribution, orderPerm)
    strokes = resample(strokes, speedProfile())              // variable point density
    strokes = lowFreqWobble(strokes, amp ~ U(0.5,3)px)       // smooth hand tremor (Perlin-like)
    strokes = jitter(strokes, sigma ~ 0.4px) ; overshoot(strokes) ; gapAtJoins(strokes)
    strokes = affine(strokes, rot ~ ±12°, scale ~ U(0.7,1.4), shear ~ ±0.15)   // keep 0/90/180/270 poses explicit
    strokes = maybeDoubleStroke(strokes) ; maybeBreak(strokes)
    leads   = addRandomLeads(strokes)                         // so stripLeads is exercised
    emit {strokes, cls: c, pose}

This gives hundreds of thousands of labelled samples for free, and it exposes a modelling question worth answering early: which symbol standard do your students draw? Resistors appear as zigzags and as boxes across syllabi; both must be classes-in-one (variant augmentation), or the model will say “unknown” to half the room.

5.2 Source 2 — Crowd data from /train exists

The simblip_sketch_templates table already receives cloud and strokes from anyone using /train. This is the real-world distribution: real hands, real devices (mouse, pen, finger). Use it as the fine-tuning set and, above all, as the test set, split by writer (all examples from one person stay together) so the score means “a person the model never met”.

  • Counts matter more than cleverness. Target ≥ 30 writers × all classes × 3 repetitions for wave 1 (≈ 30 × 60 × 3 = 5,400 symbols). That is a classroom afternoon (Section 5.5).
  • Privacy: strokes only, no identity, no free text. Add a consent line on /train saying the examples train a shared model; allow deletion. Students may be minors — get the school’s sign-off for any organised session.
  • Quality control: drop examples that S1 + the old matcher both strongly disagree with the label on (probably mislabelled), then review that disagreement list by hand — it is also a list of the confusable classes.

5.4 Source 4 — Rendered scenes with free labels (for photos)

The app can already generate many valid scenes (the SimScript corpus, the 100-question set, course figures). Because each scene is created from a known IR, rendering it to an image gives a picture with perfect labels for free (boxes, classes, connections). Then make it look like a photo: paper texture, ruled/grid lines, perspective warp, uneven lighting, shadows, blur, JPEG noise, pen-thickness changes, partial occlusion. Use this to train the detector and to test the clean-up stage. Real photographs are still required for evaluation.

Claude as annotator: Claude can read images, so for a held-out set of ~300 real photos (textbook pages, whiteboards, student notebooks — collected with permission) Claude drafts the IR by eye and Rohan or a teacher spot-checks a sample (say one in five). It is slow to label thousands that way but ideal for a small, high-quality test set.

5.5 A data-collection session (Rohan’s task)

  1. Upgrade /train to a guided mode (Phase S1): it shows “Draw: resistor” with a progress bar, three repetitions per class, random class order, a device tag (mouse / pen / finger), and a 5-second thank-you screen. Gamify lightly (a leaderboard of classes completed, not of people).
  2. Run it in one class period with 20–30 students on their own laptops and phones, with the teacher’s agreement and a short consent line.
  3. Collect 10–15 whole hand-drawn circuits and mechanics scenes per student from a printed prompt sheet (“draw a series circuit with a battery, a switch and two bulbs”). These become the end-to-end test set that no model ever trains on.
  4. Freeze it: copy to scripts/ai/sketch/testset/, hash it, never use it for training.

5.6 Dataset hygiene

  • Split by writer, never by sample. Split synthetic and real separately and report both.
  • Report per-class numbers; a single average hides that “capacitor vs battery” is failing.
  • Keep a MANIFEST.json with source, licence, count and hash for every dataset.
  • Version the class list; when a class is added, old models are retrained, not patched.

6. Training, export, shipping, memory

6.1 Where it trains

Everything here fits the author’s RTX 4060 laptop (8 GB) — in fact a CPU would nearly do for S1. Tools: PyTorch for training, ONNX for the exchange format, onnxruntime for int8 quantisation and verification, ONNX Runtime Web in the browser.

6.2 SketchNet skeleton

# scripts/ai/sketch/train/sketchnet.py   (skeleton — Claude will complete and test it)
class SketchNet(nn.Module):
    def __init__(self, n_cls, n_pose=8, seq_len=64):
        super().__init__()
        self.cnn = nn.Sequential(                       # input: 2×32×32  (full view, body-only view)
            blk(2, 16), blk(16, 32), blk(32, 64), blk(64, 96), nn.AdaptiveAvgPool2d(1), nn.Flatten())
        self.gru = nn.GRU(input_size=4, hidden_size=64, batch_first=True)   # (x, y, pen_up, turn)
        self.cls  = nn.Sequential(nn.Linear(96 + 64, 128), nn.ReLU(), nn.Dropout(0.2), nn.Linear(128, n_cls))
        self.pose = nn.Linear(96 + 64, n_pose)
    def forward(self, img, seq):
        a = self.cnn(img); _, h = self.gru(seq); z = torch.cat([a, h[-1]], 1)
        return self.cls(z), self.pose(z)
# loss = CE(cls, label_smoothing=0.05) + 0.5·CE(pose) ; AdamW, cosine schedule, 30–60 epochs
# augment on the fly: re-run the synthetic wobble on stored vector strokes (never augment a rendered image only)
# after training: temperature-scale on validation → export ONNX (opset 17) → onnxruntime int8 → check |logit diff| < ε

6.4 Shipping

  • Format: ONNX int8 files (sketchnet-v1.onnx, inkchars-v1.onnx), content-hashed, versioned in a small models.json manifest shared with the Tutor’s manifest (Doc 1, Section 5.4).
  • Runtime: ONNX Runtime Web (WASM, SIMD, threads when cross-origin isolated; WebGPU provider when present). Its WASM binary is the real first-load cost (on the order of ten megabytes est.) — lazy-load it after the first pen-hold, cache it, and show a small “learning to read your drawing…” first-time state. If that proves too heavy for the always-on feel, S1 and S3a (a few hundred thousand parameters) can be run by a ~150-line hand-written TypeScript forward pass instead; decide with the Phase S2 numbers.
  • Threading: run in a Worker beside the Tutor’s worker; never on the main thread (physics owns it).
  • Hosting: the files are small enough to serve from the app’s own static assets; the optional VLM goes to the same object storage as the Tutor’s weights.
  • Credits: every dataset and model goes into scripts/third-party-licenses.mjs, and the “Rohan Singh” credit rule for public surfaces applies to any “powered by” text.

7. How to build it: phases and exit criteria

Rule of this plan: build the pipeline around the models before the models. A deterministic compiler with hand-written IR can be fully tested on day one; the existing recogniser stands in for S1 until the new one beats it on a fair test.

Phase S0 — IR, compiler and gold tests M

  • Build: lib/sketch/ir.ts (zod schema, Appendix A), lib/sketch/compile.ts (circuit + digital first), pin-name tables derived from terminalsOf() and the anchor list in the SimScript reference, lib/sketch/compile.test.mjs.
  • Gold set: write ~40 IR files by hand (or have Claude write them from textbook circuits and verify) under scripts/ai/sketch/gold/: series/parallel, divider, RC, rectifier, transistor switch, op-amp amplifier, gate networks, flip-flop counter.
  • Tests: every gold IR compiles → lintSimScript clean → engine runs; compiled scenes render with the auto-layout engine; wrong IR (missing pin, unknown class) produces a clear error, not a crash.
  • Exit: 40/40 gold IR compile, lint, and simulate; compile time < 20 ms each.

Phase S1 — Data foundations M

  • Build: the synthetic stroke generator (Section 5.1) with a CLI that writes a sharded dataset and MANIFEST.json; guided /train mode; export script for the cloud table → local dataset (writer-split); the class list generated from COMPONENTS.
  • Rohan: run the collection session (Section 5.5); the end-to-end test set is frozen here.
  • Exit: ≥ 200 k synthetic samples; ≥ 30 writers’ real data; the baseline (existing CART + $P matcher) scored on the real test set — this number is what S2 must beat.

Phase S2 — SketchNet v1 M

  • Build: training script (Section 6.2), calibration, ONNX int8 export, lib/sketch/sketchnet.ts (worker wrapper + pre-processing identical to training — a shared test vector file guards against train/serve skew), feature flag in canvas.tsx pen+hold path with fallback to the old matcher.
  • Tests: golden input → golden logits (Python ↔ browser, within tolerance); latency and memory on the reference devices; flag off = behaviour unchanged.
  • Exit: real-test top-1 beats the baseline and reaches the target in 1.5 (or the gap is explained); < 5 ms per symbol; always-on bundle size recorded and in budget.

Phase S3 — Wires, values, ghost UI L

  • Build: grouping and wire/junction extraction (S0 extended), S3a ink characters + unit grammar, label association, ghost overlay + tap-to-correct + “Make it live” as one undo step, doubts list, correction capture (local first, opt-in upload).
  • Exit: on the whole-circuit test set, ≥ 80% behavioural equivalence (or the failure analysis is written and the next fix named); median taps-to-correct ≤ 2.

Phase S4 — Mechanics and optics L

  • Build: mechanics classes and relations (ramp, ground hatching, block, ball, spring, rope, pulley if a component exists — otherwise report the gap), arrows → forces/velocities, label → parameter mapping, compiler paths with x/y; optics left-to-right.
  • Exit: a set of 30 gold situation sketches (“block on a 30° ramp with friction”, “two masses over a pulley”, “convex lens with object at 2f”) run and match expected motion/ray behaviour.

Phase S5 — Photo path L

  • Build: clean-up (perspective correction, adaptive threshold, thinning), connected components → S1, pixel wire tracing (skeleton + junction detection), S3b label crops, synthetic-photo generator (5.4), real-photo evaluation set labelled with Claude’s help.
  • Decision point: if recall on real photos is poor, fine-tune and ship a nano detector (S2 model in 4.1); otherwise skip it.
  • Exit: ≥ 70% scene-level correctness on clean printed circuits; transient memory measured; no download beyond the always-on bundle (unless the detector was needed).

Phase S6 — VLM evaluation and tutor tools M

  • Build: evaluate SmolVLM-256M/500M on 100 real figures for the three allowed jobs (4.6); ship only if it adds measurable value over S5. Implement sketch.recognize and sketch.to_scene in the Tutor’s tool registry (Doc 1, Section 4), with the memory lease. Teaching moves: “here’s what I read”, polarity and open-circuit mistakes.
  • Exit: a student can photograph a textbook circuit, see the ghost preview, fix one wire, make it live, and ask the tutor “why does the LED not light?”.

7.1 Working agreement for Claude

  1. Every stage emits the IR and has a unit test on hand-written input before any model touches it.
  2. No metric is reported without the writer-independent real test set. Synthetic numbers are labelled “synthetic”.
  3. The frozen test sets (testset/, hash in MANIFEST.json) are read-only in training scripts — enforce with a hash check that fails the run.
  4. A feature flag guards every user-visible change; the old recogniser remains the fallback until a phase exit says otherwise.
  5. Commit, merge and verify the deployment after each edit (standing rule); append decisions to docs/ai/decisions.md.

9.2 Open questions

  1. Which symbol standards do your target colleges actually draw? (A 20-minute survey of two or three teachers answers this and may remove classes.)
  2. Is pen/tablet the main input, or mouse and touch? Pressure and stroke dynamics differ; the collection session must mirror real use.
  3. Does the VLM earn its place? Decide from S6 evidence, not enthusiasm.
  4. Which mechanics symbols are missing as components (pulley, pivot, incline presets)? Each gap is either a new component (which then needs engine support) or an out-of-scope note.

9.3 Decisions that are Rohan’s

  • Approving the symbol taxonomy and the standards it covers.
  • Organising and consenting the data-collection session.
  • Whether student corrections may be uploaded to the shared model by default (recommended: opt-in).
  • Whether photo import ships in wave 1 or waits until the live-ink path is excellent (recommended: wait).

Appendix A — Scene IR (full schema)

// lib/sketch/ir.ts
import { z } from 'zod'
const Rot = z.union([z.literal(0), z.literal(90), z.literal(180), z.literal(270)])
const Node = z.object({
  id: z.string(),
  cls: z.string(),                          // validated against COMPONENTS ∪ MECH_PRIMITIVES at compile time
  conf: z.number().min(0).max(1),
  alt: z.array(z.object({ cls: z.string(), conf: z.number() })).max(3).optional(),
  bbox: z.tuple([z.number(), z.number(), z.number(), z.number()]),
  rot: Rot, flip: z.boolean().optional(),
  values: z.record(z.string(), z.string()).optional(),
  source: z.enum(['ink', 'photo']),
})
const Pin = z.object({ node: z.string(), pin: z.string() })     // pin names = SimScript anchors (.positive, .a, .anode, .in1 …)
const Edge = z.object({ a: Pin, b: Pin, kind: z.enum(['wire','rope','rod','spring','damper']), conf: z.number() })
const Label = z.object({ text: z.string(), bbox: z.array(z.number()).length(4), attachedTo: z.string().optional() })
const Doubt = z.object({ ref: z.string(), why: z.enum(['low-confidence','ambiguous-junction','dangling-wire','unreadable-value']) })
export const SketchIR = z.object({
  domain: z.enum(['circuit','digital','mechanics','optics','diagram']),
  nodes: z.array(Node), edges: z.array(Edge), labels: z.array(Label), doubts: z.array(Doubt),
})

Appendix C — Worked example: from ink to running scene

The user draws: a vertical double-line with the longer line on top (battery), a zigzag labelled “1k”, a triangle-with-bar (diode) pointing the wrong way, and wires joining them in a loop. They hold the pen.

// S0 groups 3 symbol-strokes-sets + 4 wires.   S1 → [battery 0.97 rot 90, resistor 0.95, diode 0.88 rot 180]
// S3a reads "1 k" next to the zigzag → values {R:'1k'}.   Wires end within tolerance of pins → edges.
{
  "domain":"circuit",
  "nodes":[ {"id":"n1","cls":"battery","conf":0.97,"bbox":[40,60,30,60],"rot":90,"source":"ink"},
            {"id":"n2","cls":"resistor","conf":0.95,"values":{"R":"1k"},"bbox":[120,50,60,24],"rot":0,"source":"ink"},
            {"id":"n3","cls":"diode","conf":0.88,"alt":[{"cls":"led","conf":0.09}],"bbox":[220,60,40,30],"rot":180,"source":"ink"} ],
  "edges":[ {"a":{"node":"n1","pin":"positive"},"b":{"node":"n2","pin":"a"},"kind":"wire","conf":0.96},
            {"a":{"node":"n2","pin":"b"},"b":{"node":"n3","pin":"anode"},"kind":"wire","conf":0.92},
            {"a":{"node":"n3","pin":"cathode"},"b":{"node":"n1","pin":"negative"},"kind":"wire","conf":0.95} ],
  "labels":[], "doubts":[{"ref":"n3","why":"low-confidence"}]
}
// Compiler (no model, no x/y → auto-layout draws it):
var n1 = create("battery", {V: 9});
var n2 = create("resistor", {R: 1000});
var n3 = create("diode", {});
connect(n1.positive, n2.a);
connect(n2.b, n3.anode);
connect(n3.cathode, n1.negative);
graph.plot(n2.I);

Unspecified battery voltage is the one place the compiler uses a default (9 V here) and records it as a doubt so the ghost preview asks “battery voltage?”. Here the diode’s pose (rot 180) places the anode on the resistor side, which is correct for forward conduction when the battery’s positive terminal feeds the resistor; had the user drawn it reversed, the IR would show it faithfully, the simulation would show no current, and the tutor (Doc 1) can turn that into the lesson “why is there no current?”. (Pin/anchor names above follow the SimScript reference; the exact pose-to-anchor mapping is derived from terminalsOf() in Phase S0 — treat this example as illustrative.)
